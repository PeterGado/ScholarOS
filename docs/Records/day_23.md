# Day 23

A polished demo can show what a product might do.

A repeated workflow shows whether it actually helps.

The frontend is built with React and TypeScript. It uses TanStack Query for server-state fetching and caching, and Zod for runtime validation at selected client boundaries.

Those choices help with the less glamorous parts of a product: loading and refreshing data, handling request state, and checking the shape of responses. But a clean component tree or a responsive loading state doesn’t prove the workflow is useful.

For ScholarOS, the real test is still the everyday sequence: finding a source, remembering why it mattered, and carrying that context into the next task. Engineering quality should make that flow reliable—not become the story by itself.

What would make a research or writing tool feel simple enough to keep using? What makes you stop using one?
