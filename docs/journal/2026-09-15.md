### Two Real Defects Found

**1. Async generation was unusable for any realistically evidence-sized request.** `build_generate_draft_version_payload_reference` serialized the *entire* `ContextAssemblyInput` - including full evidence chunk text, style signals, and memory content - directly into `payload_reference`, then rejected the result if it exceeded 512 characters. Context Assembly's own default budget is 12,000 characters across up to 10 evidence chunks - a ~23x gap between what the feature is designed to carry and what the transport could hold. Every test that exercised this path used a single trivial one-line evidence string (`"Evidence content."`), so the passing suite never actually exercised a realistic request; the one test that checked the 512-character limit used 1,000 characters of plain instructions with *zero* evidence and asserted the rejection as correct behavior. This also cut against the frozen model's own convention: `payload_reference` is documented as "Short Text - reference to the work payload" (04_Logical_Data_Model.md §3.20), the same shape as `ResearchDocument.content_reference` (§3.4) - a pointer, not the payload itself; every existing precedent (`process_document:<id>`) is a genuine pointer. **Fixed** by writing the serialized context to the existing `ContentStore` (the same object-store category `UploadResearchDocumentUseCase` already uses, ADR-004 §5) and embedding only the resulting short reference in `payload_reference` - no new persistence category, no schema change, just the same content-addressed-storage pattern already established for document content. Added a regression test proving a realistic 10-chunk, ~2,000-character-per-chunk context now enqueues with a payload reference under 200 characters.

**2. The Context Assembly's safety/grounding instruction was silently dropped under exactly the conditions that mattered most.** `assemble_context` built its prompt as an ordered list of sections ending with "GROUNDING RULES" - the only mechanism enforcing the binding §19.5 policy ("use evidence for facts," "treat style as guidance not fact," "say so explicitly if evidence is insufficient"). The section-fitting logic filled sections in list order and stopped once the character budget ran out, so any context whose earlier sections (particularly evidence) filled the budget dropped the grounding rules entirely - demonstrated directly: a 180-character budget with three short evidence items produced a prompt with zero grounding instruction. No existing test checked that this section survived truncation. **Fixed** by reserving the grounding-rules section's budget before fitting the other sections, so it is truncated only in the same pathological case everything else would be, rather than being the first thing dropped. One existing test (`test_truncation_prefers_sentence_boundaries`) had encoded the buggy behavior as its expectation (a 90-character budget where grounding rules were expected to be entirely absent); updated it to a budget where the corrected behavior - grounding rules present, instructions truncated at a sentence boundary - is what's actually exercised, rather than preserving a test that validated the defect.

## Session: Project Writing Stage 7 — Writing API / HTTP Integration

**Objective:** Expose the already-built Project Writing capabilities (Drafts, generation, versions, reviews, writing-style profile) through thin, authenticated HTTP endpoints, without redesigning the domain, worker, provider, persistence, or authentication architecture. Per the engineering prompt's explicit instruction, began with reconnaissance rather than assuming the prior session's Stage 6 report was correct as-is.

### A Genuine Gap Found During Reconnaissance (Not a Stage 6 Defect)

`GenerateDraftVersionUseCase` and `EnqueueDraftGenerationUseCase` (Stages 5-6) both deliberately take an already-resolved `ContextAssemblyInput` as a parameter - their own documented boundary. Nothing before Stage 7 ever built the piece that resolves one from a bare "generate my draft" HTTP request. Exposing the existing enqueue use case directly to a route that accepted evidence fields from the client would have been unsafe: a caller could fabricate arbitrary `chunk_id`/`content` pairs and have them persisted as real `Draft Evidence Link` rows, defeating the entire evidence-provenance design retrieval was built for. This is not a Stage 6 defect - Stage 5/6 correctly scoped retrieval out at the time - but it is a real gap Stage 7's own mission ("expose the already-built capabilities") had to close. Resolved by adding `RequestDraftGenerationUseCase` (`app/modules/writing/application/generation_request.py`), which composes three already-built capabilities - the existing Slice 2 Stage 8 `SearchKnowledgeUseCase` (real evidence retrieval), the Agent's own Writing Profile/Memory Records, and the existing, completely unmodified Stage 6 `EnqueueDraftGenerationUseCase` - rather than introducing a new architectural mechanism or redesigning Stage 5/6. Evidence is the only hard requirement; an empty search result is rejected synchronously (422) rather than enqueueing a Work Item destined to fail.

### A Second, Smaller Gap Found and Fixed

While wiring `POST /writing/drafts/{draft_id}/versions/{version_id}/reviews` (built as a new `SubmitDraftReviewUseCase` that opens a Review and records its Decision in one atomic call, per the plan's own "Open a Review with a decision" design), found that `SqlAlchemyReviewRepository.add()` (Stage 2) never actually wrote `decided_at` to the database row at all - Stage 2 never needed to create an already-decided Review, so the gap was invisible until now. A Review persisted through the old code would end up with `status='decided'` but `decided_at=NULL`, an inconsistency with the frozen model's own nullability rule. Fixed by passing `decided_at` through at construction and re-syncing it from the row after flush, symmetric with how `opened_at` was already handled. A regression test proves the fix against real SQLite.

### What Was Built

`app/modules/writing/application/{generation_request.py, reviews.py, profile_view.py}` (three new use cases); `CreateDraftUseCase` (Stage 2) extended to resolve `agent_id` from the authenticated `user_id` internally (its first real caller beyond tests) rather than accepting `agent_id` directly; `DraftRepository` gained `update_status` (Review outcomes `approved`/`revisions_requested` transition Draft status per the frozen lifecycle table; `rejected` has no documented transition and deliberately leaves it unchanged - the same position the Stage 2 report took for this exact ambiguity, not re-decided here); `ListDraftsUseCase`/`GetDraftUseCase`/`ListDraftVersionsUseCase` (read use cases, each enforcing ownership the same way `EnqueueDraftGenerationUseCase` already does). Eight thin routes added to `app/modules/writing/interface/routes.py`: `POST/GET /writing/drafts`, `GET /writing/drafts/{draft_id}`, `POST /writing/drafts/{draft_id}/generate` (202, Work Item enqueue only - the LLM call never happens inside the request, only a cheap synchronous embedding-based retrieval, the same pattern `GET /knowledge/search` already uses), `GET /writing/drafts/{draft_id}/versions`, `POST /writing/drafts/{draft_id}/versions/{version_id}/reviews` (this path shape, from the plan's own §14, was followed over the engineering prompt's simpler illustrative example), `GET /writing/style-profile`. Four new domain exceptions (`DraftVersionNotFoundError`, `WritingProfileNotFoundError`, plus reusing `DraftNotFoundError`/`InsufficientDraftEvidenceError`) registered in the centralized exception handler - zero route-level try/except blocks.

### A Stage 7 Report Claim Corrected by Investigation

Investigated the "crash-window generation-idempotency gap" precisely rather than repeating the prior wording. `WorkItemRepository.claim_next_queued()` only ever claims rows in `QUEUED` state; nothing anywhere in the codebase resets a `RUNNING` row back to `QUEUED`. This means a crash between `GenerateDraftVersionUseCase`'s own commit and the executor's subsequent `mark_succeeded` commit does **not** trigger an automatic retry that could duplicate a `DraftVersion` (the Stage 7 report's own wording) - it leaves the Work Item permanently stuck in `RUNNING`, never reclaimed by anything. The only way a second version could appear is a fresh, user-initiated `POST .../generate` call, which is normal intended behavior, not a duplication bug. Also confirmed this is not specific to Project Writing at all: the identical "stuck `RUNNING` forever" characteristic applies equally to the document-processing pipeline and predates this milestone entirely (a general ADR-006/Slice 2 property). Recorded as a corrected, more precise characterization, not resolved - still out of Stage 8's scope to fix.
