## Session: Project Writing Stage 1 — Architecture Reconnaissance, Product Reconciliation & Implementation Plan

**Objective:** Per a detailed 25-section project owner prompt, reconcile the "Agent = Project Workspace" product model and the existing Slice 2 backend against what Project Writing actually needs, without writing any implementation code, and produce a staged implementation plan.

### What Happened

Full reconnaissance across the SRS, `04_Logical_Data_Model.md`, `05_Constraints_and_Integrity.md`, `05_Backend_Architecture.md`, `04_AI_Architecture.md`, ADR-001 through ADR-010, and the actual current backend code. The single most important finding: the entire Writing/Review/Memory/Conversation/Writing-Profile data domain (`Draft`, `Draft Version`, `Review`, `Review Decision`, `Writing Profile`, `Profile Characteristic`, `Profile Characteristic Source`, `Memory Record`, `Memory Provenance Link`, `Conversation`, `Message`, `Message Context Link`) is **already fully frozen** in the Database Baseline v1 but **entirely unimplemented** in code — the same relationship Slice 2 had to Knowledge Element/Chunk before Stage 5 realized them. A second genuine gap was found: `05_Backend_Architecture.md` names no "Writing Service" domain — Draft creation sits in a blind spot between the AI Service Layer (generates, doesn't own data) and the Review Service (evaluates, doesn't create). A third open question was identified and deliberately left unresolved: similar-project material has no frozen entity that keeps it retrievable without risking evidence-confusion with the user's own research.

Produced `docs/Project_Writing_Implementation_Plan.md` (20 sections): recommends realizing the frozen Draft/Draft Version/Review model as-is (no new "WritingTask" or "Revision" entity), introducing `modules/writing/` as an additive Writing Service (no ADR needed), deferring similar-project ingestion from MVP, using a Draft-scoped Conversation/Message for per-request instructions rather than a schema correction, accepting vector-only retrieval for Writing MVP (ADR-005's hybrid gap stays open, unresolved here), reusing the existing Provider Abstraction/Work Item infrastructure unmodified, and an 8-stage build sequence (Stage 2 Writing Domain & Persistence through Stage 8 Full E2E Validation). Six items were explicitly left for project-owner approval rather than decided unilaterally.

### Decisions

The project owner approved all six open items in a single follow-up message: `modules/writing/` as the Writing Service; similar-project material deferred, no new entity yet; Draft-scoped Conversation/Message for per-request instructions; ADR-005 hybrid retrieval left open, vector-only accepted for Writing; general AI knowledge restricted to non-factual scaffolding, retrieved project knowledge remains primary; model/version metadata stored in Work Item payloads. The plan document was updated in place to record these as decisions (not recommendations) before Stage 2 began.

### Completion Status

Stage 1 complete. No implementation code, ADR, or frozen document was touched. Implementation started: NO (Stage 1's own final line) — Stage 2 authorized immediately after via a detailed follow-up prompt.

## Session: Project Writing Stage 2 — Writing Domain & Persistence

**Objective:** Per a detailed Stage 2 engineering prompt, realize the ten frozen entities identified in Stage 1 as domain + persistence, deliberately stopping before generation, retrieval, Work Items, API, or frontend work.

### What Happened

Read the approved plan, then re-verified the frozen schema directly from `04_Logical_Data_Model.md` (§3.8-§3.18, §4.2-§4.5) and `05_Constraints_and_Integrity.md` rather than working from memory, and inspected `modules/agent`, `modules/knowledge`, `modules/document`, `database/session.py`, and the existing test suite to match established conventions exactly (dataclass domain entities with `__post_init__` validation, ABC repository interfaces, SQLAlchemy 2.x `Mapped`/`mapped_column` ORM models, `init_db()` model registration).

Built `app/modules/writing/` (`domain/`, `application/`, `infrastructure/`, plus an intentionally empty `interface/` per the Stage 2 prompt's explicit instruction not to build routes yet) realizing: `Draft`, `Draft Version`, `Review`, `Review Decision`, `Draft Evidence Link`, `Writing Profile`, `Profile Characteristic`, `Profile Characteristic Source`, `Memory Record`, `Memory Provenance Link` — all ten entities identified in Stage 1, exactly as frozen, with no new fields invented. Two minimal application use cases (`CreateDraftUseCase`, `CreateDraftVersionUseCase` — the latter computing the next `version_number` from existing versions, since "current version" is a derived value per `04_Logical_Data_Model.md` §6, never a stored pointer). Registered all ten ORM models in `init_db()`.

**A deliberate scope narrowing from the Stage 1 plan, decided during Stage 2 itself:** the Stage 2 prompt's §40 explicitly cautioned against building a conversational subsystem "merely to support future prompts," and on inspection none of Draft/Draft Version/Review/Evidence/Profile/Memory's Stage 2 persistence correctness actually depends on `Conversation`/`Message`/`Message Context Link` existing yet. `Conversation` and `Message` (approved in Stage 1 §19.3 as the eventual home for per-request writing instructions) were deferred to the stage that actually needs to read them (Stage 4, Context Assembly) rather than built now — narrower than Stage 1's own data-model table, and recorded here rather than silently expanding Stage 2's scope.

**Two real defects found and fixed before completion, not papered over:**
1. SQLAlchemy's `Enum(..., native_enum=False)` type, given a Python `enum.Enum` class, stores each member's `.name` (e.g. `"OPEN"`) by default, not its documented `.value` (`"open"`) — invisible through the ORM (Python-level round-trips are unaffected either way), but it silently broke every raw-SQL CHECK constraint and partial unique index written against the frozen model's documented lowercase enumerated values. Fixed in the new Writing models via a `_enum_column()` helper using `values_callable`. **This same default is also present, unfixed, in the pre-existing `agent`/`document`/`knowledge` modules** — confirmed by direct query (`Agent.status` is stored as `'ACTIVE'`, not `'active'`) — and is reported here as a live, if currently harmless, deviation rather than silently corrected in already-shipped code outside Stage 2's authorized scope.
2. A plain composite `UniqueConstraint` on `Draft Evidence Link(draft_version_id, target_type, chunk_id, document_id)` does not actually prevent duplicate evidence annotations: SQL treats `NULL <> NULL`, so two rows sharing the same `chunk_id` with `document_id` both `NULL` are never considered equal. Fixed with two partial unique indexes (one per exclusive-arc branch), each `WHERE <column> IS NOT NULL`.

Also found, while writing the exclusive-arc validation for `Memory Provenance Link`: the frozen model lists six `source_type` values but only five nullable target-reference columns — `user_input` has no matching column. Read as "zero target references, not one" (the record was established directly from what the user said, no separate artifact to link to) rather than a modeling contradiction; documented explicitly as an implementation interpretation in both the domain entity's docstring and this report, not silently assumed.

## Session: Project Writing Stage 3 — Writing-Style Document Ingestion

**Objective:** Per a detailed Stage 3 engineering prompt, allow an authenticated user to submit writing-style source documents for a later (not-yet-built) style-extraction stage - explicitly forbidding any AI call, semantic analysis, Work Item, or Profile Characteristic generation in this stage.

### A Real Schema Gap Found and Resolved Without Inventing an Entity

Reconnaissance surfaced a genuine mismatch the prompt itself anticipated and asked to be reported rather than silently resolved: the frozen Logical Data Model has no entity for "a Research Document accepted as a writing-style sample, pending extraction." `Profile Characteristic Source` (04_Logical_Data_Model.md §4.5) - the only document-to-Writing-Profile link entity - requires a `Profile Characteristic` to already exist, which requires semantic extraction, which this stage must not perform. Resolved without inventing a new entity or a new field: writing-style samples are stored as ordinary `ResearchDocument` rows (reusing the existing entity and table exactly, per the prompt's own preference), and the "relationship with the Writing Profile" is the existing Agent-scoping chain (Research Document -> Project -> Agent <- Writing Profile) - the same "indirect association via shared Agent scope" pattern the frozen model already uses for the structurally identical Writing-Profile-to-Draft relationship (04_Logical_Data_Model.md §5: "Writing Profile — Draft (N:M): Realized indirectly"). `Profile Characteristic Source` rows remain for the future extraction stage to create once real characteristics exist.

Also decided and documented explicitly (not silently assumed): the Agent's active Writing Profile is auto-created on first style-document upload if none exists yet, atomically with the document (mirrors `CreateAgentWorkspaceUseCase`'s Agent+Project atomicity); the invariant "at most one active Writing Profile per Agent" (Stage 2's own database constraint) remains the backstop.

### What Was Built

`UploadWritingStyleDocumentUseCase` (`app/modules/writing/application/style_ingestion.py`) - resolves the Agent from the authenticated identity (never a client-supplied id), reuses the existing `ContentStore` and `ResearchDocument`/`DocumentRepository`, and - critically - takes no `WorkItemEnqueuer` dependency at all, so a style document can never enter the Knowledge Processing Pipeline the way a real research document does. `POST /writing/style-profile/documents`, a thin route mirroring `POST /projects/{project_id}/documents` exactly, wired through the existing exception-handler architecture with zero new exception classes or handler registrations (reused `AgentNotFoundForUserError`, `EmptyDocumentContentError`, `InvalidDocumentTitleError`, `InvalidDocumentFormatError`, all already mapped).

### Verification Performed

362 prior + 20 new tests (unit with fakes, integration against real SQLite + real filesystem, e2e against real HTTP via the existing `TestClient`-based suite) all pass, zero regressions. Additionally performed a genuine real-`uvicorn` manual verification (not just `TestClient`) from a fresh environment: login -> create Agent -> upload an ordinary research document -> upload two writing-style documents -> queried the live SQLite database directly and confirmed exactly one Work Item exists (from the ordinary research document only) and exactly one Writing Profile exists, correctly shared across both style uploads. Fresh-database schema check reconfirmed all 20 tables unchanged (no schema modification this stage, as expected from entity reuse). `/health` still returns 200; existing Agent/Document/Knowledge/Auth flows all re-verified working over the same real-HTTP session.

### Completion Status

Stage 3 complete. No AI call, no retrieval, no Work Item, no semantic style extraction, no Conversation/Message, and no frontend code was introduced.

## Session: Project Writing Stage 4 — Writing Style Profile Extraction & Persistence

**Objective:** Per a detailed Stage 4 engineering prompt, derive real `Profile Characteristic` rows from Stage 3's already-persisted writing-style samples via the existing `TextGenerationProvider`, with mandatory provenance - the first Project Writing stage in which semantic AI interpretation of writing style is permitted.

### Two Genuine Gaps Found and Resolved Without Redesigning Frozen Architecture

**Which samples to analyze.** Stage 3's own completion report had already flagged this: no field on `Research Document` distinguishes a writing-style sample from ordinary research material - both share the same table, scoped only by Project. A project-wide scan would silently pull unrelated research material into style analysis. Resolved per the Stage 4 prompt's own §10 guidance ("the application associates the characteristic with the samples used for extraction") and WR-010's user-driven framing: the caller supplies the exact `document_ids` to analyze explicitly; the use case validates each one belongs to the caller's own Agent before ever calling the provider. No schema change, no ADR - a use-case input design choice, not a frozen-model decision.

**Regeneration semantics are genuinely undefined by the frozen model.** `Profile Characteristic` (04_Logical_Data_Model.md §3.12) has no status column and no supersession reference - unlike Knowledge Element or Memory Record, which both have exactly this mechanism - yet `05_Constraints_and_Integrity.md` classifies it as "never tombstoned... superseded or retained, never deleted." Running extraction a second time against a profile that already has characteristics would therefore have to either violate "never tombstoned" (delete/replace) or accumulate indefinitely (no way to mark old characteristics stale) - the frozen model authorizes neither. Per the Stage 4 prompt's explicit instruction ("If the frozen architecture does not specify the update semantics, stop and report the ambiguity... rather than silently choosing a persistence strategy"), re-extraction against an already-extracted profile is refused outright (`WritingProfileAlreadyExtractedError`, 409) rather than guessed at. This is reported as an open item, not resolved.

### What Was Built

`app/modules/writing/domain/style_extraction.py` (prompt construction, strict non-coercing response parsing - mirrors `app.modules.knowledge.domain.semantic_classification`'s own discipline exactly, duplicated deliberately rather than imported to keep the two pipelines architecturally independent) and `ExtractWritingStyleProfileUseCase` (`app/modules/writing/application/style_extraction.py`): resolves ownership from the authenticated identity only, loads and decodes the named samples, calls the *existing* `TextGenerationProvider` (no new AI abstraction - a `get_text_generation_provider()` dependency was added alongside the existing `get_embedding_provider()`, both backed by the same `create_provider()` factory call), validates the entire response before any persistence begins, and persists `WritingProfile`/`ProfileCharacteristic`/`ProfileCharacteristicSource` atomically - every characteristic gets a `ProfileCharacteristicSource` row for every document actually supplied to that extraction run (deterministic, never trusting a document/source reference the model itself might return). `POST /writing/style-profile/extract`, wired through four newly-registered (already-existing exception classes') handlers - zero new exception-handling patterns.

### Verification Performed

434 total tests pass (382 prior + 52 new), zero regressions: domain unit tests (prompt determinism, strict parsing, rejecting invalid/blank/out-of-range fields, confirming a single malformed characteristic fails the whole response before persistence), application unit tests with fakes (the mandatory failure-atomicity test - one valid + one invalid characteristic in the same response leaves zero persisted rows; a persistence-layer failure rolls back the whole batch; ownership cannot be supplied by AI output; provenance cannot reference arbitrary IDs), integration tests against real SQLite + a fake provider (the mandatory provenance test - given documents A/B/C, every persisted characteristic's `ProfileCharacteristicSource` rows point only to the actual supplied documents, never a model-supplied `source_id`/`document_id`; no duplicate profile; no orphan characteristics; cross-agent document reference rejected), and e2e tests over real HTTP with a provider dependency override (201/401/404/409/422/502/400 paths). Additionally verified over a genuine real-`uvicorn` run with no `AI_API_KEY` configured: the new endpoint correctly surfaced the *existing* `ProviderConfigurationError` -> 503 contract with zero new code for that path, and all Stage 1-3 flows (health, login, agent creation, research-document upload, style-document upload) re-confirmed working unmodified. Database schema re-inspected: still exactly 20 tables, no new or altered columns.

### Completion Status

Stage 4 complete. No draft generation, no review workflow, no writing memory, no new AI provider abstraction, no Work Item, and no frontend code was introduced. Two items are explicitly reported as open rather than silently resolved: which samples belong to a style profile (resolved via explicit caller input, not a schema change) and regeneration semantics for re-running extraction (refused outright, pending a project-owner decision).
