**A real bug, caught by testing over genuinely separate HTTP requests rather than a shared test session:** `AuthSessionRepository.create()`/`.end()`/`.touch()` only ever `flush()`, never `commit()`. Every Stage 2-4 test exercised login-then-verify within one shared `Session` object, so the missing commit was invisible — flushed-but-uncommitted rows are visible within their own open transaction. Over real HTTP, each request gets its own `Session` from `get_db()`, and `Session.close()` without a prior commit silently rolls back uncommitted work (SQLAlchemy's default). The first version of the login/logout tests caught this immediately (login succeeded, logout on the same token then failed with 401 instead of 204). Fixed properly, not around: gave `AuthService` a `UnitOfWork` dependency — exactly the same pattern `CreateAgentWorkspaceUseCase` already uses — and had `login()`/`logout()`/`verify_token()` each commit on success, rollback on any exception.

### Architectural Reasoning

* All Authorization-header failure modes (missing, wrong scheme, malformed) collapse into the same `InvalidSessionError` → 401 as an unknown/ended token. No security reason to distinguish them to the client, and it keeps the exception model to two types instead of proliferating status codes per parsing edge case.
* Login returns 200, not 201: a login response is meaningful to the client as "here is your token," not as a resource representation, even though a `Session` row is technically created.
* The `UnitOfWork` fix was the only way to correct the bug without duplicating commit logic in the routes or reintroducing manual `db.commit()` calls into tests (which is exactly what had been silently masking the bug in Stage 3-4's own test file, now removed).
