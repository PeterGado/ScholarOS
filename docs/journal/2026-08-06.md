### Architecture Summary (CTO-level)

ScholarOS is architected as an **intelligent research operating environment**, not a writing tool: a layered, modular system in which an orchestrated intelligence layer (context assembly, knowledge processing, retrieval, drafting, review, reflection) operates on a persistent, evidence-grounded data core, all behind human oversight. The architecture is deliberately implementation-agnostic; the ADR set now pins the decisions that matter:

- **One deployable system, modular by design** — a modular monolith (ADR-003) with seven logical service boundaries, so we get a solo-developer-friendly MVP *and* a credible path to microservices if evidence demands extraction.
- **Provider-agnostic intelligence** — all AI capabilities sit behind a gateway (ADR-002); swapping or adding providers is configuration, not code. This is our hedge against the fastest-moving part of the market.
- **Hybrid retrieval as the product moat** — lexical + semantic retrieval with reciprocal rank fusion over evidence-linked chunks (ADR-005): academic precision *and* paraphrase recall, with every retrieved item traceable to source.
- **Memory is a first-class persisted domain** (ADR-004), not a cache — project understanding survives sessions, which is the product's core continuity promise.
- **Async-first pipelines** (ADR-006) keep the UI responsive while ingestion, indexing, drafting, and review run as durable, retryable, observable work.
- **Local-first, cloud-ready** (ADR-007): the MVP runs as a single containerizable process with backups from day one; persistence and workers migrate to managed services without architecture change.
- **Scaling by lever, not redesign** (07 §5): single user → research teams → universities → enterprise → SaaS maps to documented levers (async decoupling, boundary extraction, stateless API tier, index partitioning, persistence swap) with five invariants that never change.

## Teaching Report — Milestone 4 (Senior-Engineer Mentoring)

Each ADR embeds full teaching content (concept, why, alternatives, trade-offs, industry terminology, real-world examples). Summary of the decisions and why they are industry practice:

1. **Provider gateway (ADR-002):** LLM/model gateway — the industry-standard answer to AI-provider volatility (used by LiteLLM, Portkey, enterprise gateways). ScholarOS's requirement is stricter than most: AIR-040 makes provider replaceability a *platform* property, so the gateway is an architectural boundary, not a utility.
2. **Modular monolith (ADR-003):** monolith-first, extract-when-it-hurts — the strategy Shopify and GitHub scaled with. The mistake to avoid is the big ball of mud; the architecture's seven service boundaries are the antidote because extraction becomes interface design, not archaeology.
3. **Hybrid retrieval with RRF (ADR-005):** lexical + semantic retrieval with reciprocal rank fusion is the standard finding in IR research and production RAG — BM25 alone misses paraphrase, pure vectors miss exact terms and quotations, which academic work demands. RRF avoids score-normalization tuning between incomparable systems.
4. **Memory as a persisted domain (ADR-004):** treating project memory as a cache (or log replay) would make understanding lossy; persistence makes it queryable, traceable, and exportable — a first-class domain per 04 §8.
5. **Outbox + in-process queue (ADR-006):** the durable outbox solves the dual-write problem (state + event persist atomically) so crashes lose no work, without a broker; the broker becomes a mechanical swap when workers are extracted.
6. **Local-first, container-ready (ADR-007):** single-node MVP with a container image from day one is the cheapest insurance against environment drift and the zero-cost path to cloud — the architecture stays visible and testable before infrastructure obscures it.
7. **Scalability by lever, not redesign (07 §5):** each growth stage (single user → research teams → universities → enterprise → SaaS) maps to a documented lever (async decoupling, boundary extraction, stateless tier, index partitioning, persistence swap) with five invariants that never change.

### 6. Teaching Report

**Why architecture freezes exist.** Architecture documents are the load-bearing floor of the build. Every later document — database schema, API contracts, code — derives from them, so every edit to the floor shakes everything standing on it. Industry teams freeze architecture at the end of the design phase for the same reason a civil engineer signs off the foundation drawing: it makes downstream work deterministic. ScholarOS's freeze (04 §4.4) is deliberately *narrow* — corrections are always allowed, and new decisions enter as ADRs, so the freeze protects stability without blocking change.

**Why ADRs are frozen.** An ADR is a decision record, not living prose. Once a decision is accepted, its value is that it is *stable*: the next engineer can trust that ADR-004's storage choice is the decision the system was built on. Rewriting a decided ADR destroys that trust and erases the historical record of *why* the team chose this path. The industry practice is to treat ADRs as append-only: when the decision changes, you write a new ADR that supersedes or amends the old one, keeping both in the record.

**Why adding documents after freeze is harmful.** The freeze rule does not say "no new documents" — it says *no new documents outside the agreed plan*. Every document is a maintenance commitment: a consistency surface, a cross-reference node, and a traceability obligation. Adding a speculative architecture document (e.g., a hypothetical "08_Microservices" plan) would create debt with no requirement backing it — the exact failure the close-out audit is designed to catch. ScholarOS documents are created only when a milestone genuinely requires them, which keeps the documentation cost proportional to the project's real needs.

**What technical debt really means.** Debt is deferred work that has a cost you will pay later — not every imperfection. The register above distinguishes real debt (TD-004 retrieval tuning, TD-005 stack validation) from non-debt (deferred-but-scoped items like TD-007 multi-tenancy, which have a triggering milestone and are *not* obligations today). The discipline is to name the debt, record *why* it is deferred, and assign the milestone that will pay it down — exactly what the register does.

**How enterprise teams transition from architecture into database design.** In enterprise practice the transition is a change of *document kind*, not a change of team: the architect hands off a stable architecture (system boundaries, data domains, storage strategy) and the database designer produces schema-level artifacts (ERDs, tables, migrations) that must be *provable* against the architecture — every table traces to a data domain in 03, every storage choice to ADR-004, every migration to the retention rules in 07 §3. ScholarOS mirrors this: database design (`docs/database/`) is grounded in 03 and ADR-004, and its deliverables (ERD, schema, migration, indexing) must each carry traceability back to the frozen architecture. The freeze is what makes this handoff safe — the database designer works against a floor that will not move beneath them.
