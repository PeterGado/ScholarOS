## Session: Stage 4 — Mechanical Extraction & Chunking

**Objective:** Per a detailed Stage 4 engineering prompt, implement `ProcessDocumentUseCase`: retrieve a stored Research Document, extract text, normalize it, and divide it into deterministic, traceable chunks.

### A Real Architectural Conflict Found and Resolved Before Any Code

The prompt itself instructed: determine whether AI provider involvement is actually required before using it, and do not send document content to an LLM merely because the gateway now exists. Reconnaissance against `02_Domain_Model.md` §4, `02_System_Components.md` §3.3, `04_AI_Architecture.md` §7, and `04_Logical_Data_Model.md` §3.5/§3.7 found a genuine, unresolved conflict: `KnowledgeChunk.element_id` is a not-null foreign key, and every `Knowledge Element` type (concept/theme/method/claim/relationship) means genuine semantic interpretation everywhere it is defined in this project's documents — there is no enum value for "raw, uninterpreted excerpt." A Stage 4 that performs no semantic interpretation (as instructed) therefore cannot legitimately persist `KnowledgeElement` or `KnowledgeChunk` rows without either inventing a dishonest placeholder or reversing course and calling the provider anyway.

Stopped and presented this to the project owner with three concrete options before writing any code. The project owner's answer (transient chunks, no fake semantic records) was implemented exactly: **`TextChunkCandidate`**, a new, deliberately transient domain value object (`app/modules/knowledge/domain/entities.py`), is Stage 4's actual output — never persisted, never mistaken for a `KnowledgeChunk`. Real semantic extraction and persistence of `KnowledgeElement`/`KnowledgeChunk`/`ChunkEvidenceLink` moves to a renamed Stage 5 ("Semantic Extraction & Persistence"), which will consume Stage 4's output. `docs/Backend_Slice2_Implementation_Plan.md` was corrected in place (not silently rewritten) to reflect this, adding one stage overall (final stage renumbered 9). No ADR was needed — no frozen entity's shape changed.

### What Was Built

`app/modules/knowledge/domain/`: `entities.py` (`TextChunkCandidate`), `text_extraction.py` (`DocumentTextExtractor` protocol + `PlainTextExtractor` — the first and only supported format is content that decodes as UTF-8 text; binary formats are explicitly deferred, not silently promised), `text_normalization.py` (deterministic: line-ending unification, per-line trailing-whitespace removal, collapsing 2+ blank lines to one — nothing more; headings, lists, quotations, and indentation are never touched), `chunking.py` (deterministic, paragraph-aware, offset-exact chunking; a 1000-character target size and no overlap are documented as implementation-level defaults, not product requirements), `exceptions.py` (`MissingStoredContentError`, `UnsupportedDocumentFormatError`, `EmptyExtractedTextError`). `app/modules/knowledge/application/use_cases.py`: `ProcessDocumentUseCase` — makes no AI provider call, writes nothing to the database, and is idempotent by construction (no persistence side effect exists to duplicate). `app/modules/document/domain/ports.py`'s `ContentStore` Protocol widened to declare `read`/`exists` (already structurally implemented by `FilesystemStorage`, just not previously declared on the port). `app/modules/document/domain/exceptions.py` gained `ResearchDocumentNotFoundError`.

47 new tests: extraction (valid/empty/malformed/binary), normalization (line endings, whitespace, paragraph preservation, determinism), chunking (short/exact-boundary/multi-chunk/long-paragraph/single-huge-word/empty/deterministic/ordering), the use case (all failure paths, idempotency, real SQLite + real filesystem integration), and an automated architecture-compliance test (AST-based import check) proving the knowledge domain/application layers import no FastAPI/SQLAlchemy/httpx/bcrypt/concrete infrastructure. Five review passes performed (Senior Backend Engineer, Principal Software Architect, Data Architect, AI/Knowledge Systems Engineer, Independent Code Reviewer) — no genuine defects found; confirmed via grep that no `app.ai`/provider reference exists anywhere in `modules/knowledge/` except in explanatory docstrings, and that `ProcessDocumentUseCase` never calls `.save()`/`.add()`/`.commit()`/`.flush()`.

### Verification Performed

Full pipeline exercised against a real uploaded document, real SQLite, and real filesystem storage: extraction → normalization → chunking → every chunk traceable to its source document by `document_id`; explicit negative assertions confirm zero `KnowledgeElement`/`KnowledgeChunk`/`ChunkEvidenceLink` rows are ever created and `processing_status` is never mutated by this stage.

## Session: Stage 6 — Async Dispatch

**Objective:** Wire document upload to enqueue a Work Item, and build an in-process executor that drains the queue and runs Stages 4+5 as one execution, making `ResearchDocument.processing_status` transitions real for the first time.

### What Was Built

`app/workers/` gained `entities.py` (`WorkItem` domain dataclass, mirroring `app.auth.entities.AuthSession`'s split from its ORM counterpart), `payloads.py` (the shared `"process_document:<document_id>"` format, used by both the enqueue site and the executor so they can never drift), `repository.py` (`WorkItemRepository`: `enqueue`, `claim_next_queued`, `mark_succeeded`, `mark_failed` with bounded retry), `ports.py` (`WorkItemEnqueuer` Protocol - a real dependency-direction fix caught before it shipped: `UploadResearchDocumentUseCase` must not depend on the concrete `WorkItemRepository` any more than it depends on concrete SQLAlchemy elsewhere), and `executor.py` (`process_one_work_item` - one claimed item, fully processed, three independently-committing phases: claim, execute, record outcome; `WorkItemExecutorLoop` - a thin `asyncio` polling wrapper).

`DocumentRepository` gained `update_processing_status` - previously no write path existed for `processing_status` at all. `UploadResearchDocumentUseCase` now enqueues a Work Item inside its existing transaction (the outbox discipline: one commit, both writes). `main.py`'s lifespan starts the executor only when `AI_API_KEY` is configured - a no-op otherwise, mirroring `sync_configured_user`'s own "optional until configured" pattern, so no existing test or deployment needs AI configuration to keep working.

`ResearchDocument.processing_status` semantics, now real: `pending` (uploaded, queued) → `processing` (claimed) → `processed` (success) or, on failure, back to `pending` while a retry is still pending, or `failed` once `DEFAULT_MAX_ATTEMPTS` (3) is exhausted - no new enum value invented.

14 new tests: unit (payload round-trip, malformed references), integration (`WorkItemRepository` against real SQLite - enqueue/claim/retry-then-terminal-failure; `process_one_work_item` end-to-end with a fake provider - success, mid-pipeline failure, retry exhaustion, empty-queue), and one e2e test exercising the entire loop over genuinely separate operations: a real HTTP upload, then a separate executor step against the same real database, then a fresh read confirming real persisted, evidence-linked knowledge.

## Session: Stage 7 — Embedding & Vector Index

**Objective:** Embed each persisted Knowledge Chunk via the provider gateway and realize the vector-index table (brute-force cosine, no new dependency), proving chunks are genuinely retrievable by similarity.

### What Was Built

Rather than a second pass re-fetching the same chunks, `ExtractDocumentKnowledgeUseCase` (Stage 5) was extended to also embed each chunk within its existing atomic "gather from the provider, then persist" phase - classification and embedding are gathered together before any persistence begins, so a failure in either leaves nothing written for that document, exactly the same atomicity guarantee Stage 5 already had. Added: `ChunkEmbedding` domain entity, `KnowledgeChunkEmbeddingRepository` interface (`add`, `list_by_agent_id` - scoped via a join through Knowledge Chunk, since the embeddings table itself carries no `agent_id`), its SQLAlchemy realization (JSON-encoding/decoding the vector, per the Implementation Plan's own storage-format decision), and `app/modules/knowledge/domain/vector_similarity.py` (`cosine_similarity`, `rank_by_similarity` - pure, deterministic, no I/O, tie-broken by `chunk_id` for reproducible ordering).

`process_one_work_item`/`WorkItemExecutorLoop` and `main.py`'s composition both updated to pass an `EmbeddingProvider` and `embedding_model_version` alongside the existing `TextGenerationProvider` - in practice the same `OpenAICompatibleProvider` instance satisfies both Protocols, so no second provider object is created.

39 new tests: unit (11 cosine/ranking correctness cases - identical/orthogonal/opposite vectors, scale invariance, zero-magnitude defensive floor, dimension-mismatch rejection, deterministic tie-breaking; plus embedding-failure atomicity added to the existing Stage 5 unit suite) and integration (embeddings verified as genuinely persisted with the correct `chunk_id`/vector/model-version against real SQLite; a real end-to-end similarity search across two agents' chunks proving agent-scoping and correct ranking; an embedding-failure-requeues-like-any-pipeline-failure case added to the Stage 6 executor suite).

### Verification Performed

278/278 tests pass (263 prior + 15 new: 11 cosine/ranking unit tests, 2 vector-index integration tests, plus one embedding-failure test added to each of the existing Stage 5 unit and Stage 6 integration suites), zero regressions. Fresh-environment script (real SQLite, real filesystem, a fake provider implementing both Protocols) confirmed the complete loop: upload → executor claims and runs the pipeline → embedding persisted with the correct model-version tag → `rank_by_similarity` against a real query vector correctly retrieves the chunk (similarity ≈ 1.0 for a matching vector). No `numpy` dependency added (pure Python, per the Implementation Plan's own recommendation); dependency-direction and no-logging checks remain clean.

### Completion Status

Stage 7 complete. **AI provider usage: YES** — one embedding call per chunk, alongside the existing classification call; this is the last provider call the Knowledge Processing Pipeline needs before it can be searched. ## Session: Stage 8 — Retrieval Endpoint

**Objective:** `GET /knowledge/search` - authenticated, agent-scoped vector search over the caller's own Knowledge Chunks, per the project owner's explicit requirement list (agent-scoped; reuse the existing `EmbeddingProvider` and `rank_by_similarity`; return document/chunk provenance without raw vectors; sensible top-K; clean empty-knowledge-base handling; no PostgreSQL/pgvector; no writing/LLM endpoint; no Stage 5 model changes; tested with fakes + real SQLite; an explicit cross-agent authorization test).

### A Flagged, Not Silent, Partial Realization of ADR-005

The project owner's requirement list specifies vector search only - no lexical search, no RRF fusion - while ADR-005 Decision 1 mandates hybrid retrieval (lexical AND semantic, fused). Implemented exactly what was specified: vector-only search for Stage 8. This is recorded here explicitly as a deliberate, partial realization of ADR-005 for the smallest testable retrieval slice, not a silent contradiction of the ADR - lexical fusion remains a documented, addable extension (ADR-005's own fusion contract is designed for exactly this), not abandoned. The project owner separately confirmed the architectural point that the current JSON-vector-table + application-side cosine approach must not quietly become the permanent production architecture; a future PostgreSQL/pgvector migration is explicitly deferred to its own decision, not something this stage introduces.

### What Was Built

`app/modules/knowledge/application/retrieval.py`: `SearchKnowledgeUseCase` - resolves the caller's own Agent from `user_id` (never accepts one from the client, the same principle Stage 6 established for document ownership), returns `[]` for an Agent with no knowledge yet (200, not an error) but raises `AgentNotFoundForUserError` for a user with no Agent at all (404 - the two conditions are deliberately not conflated), embeds the query via the existing `EmbeddingProvider`, ranks via the existing `rank_by_similarity` (no new AI abstraction, no new ranking algorithm), and assembles evidence (document id/title) per result via a new `ChunkEvidenceLinkRepository.list_by_chunk_id` (the reverse direction of the existing `list_by_document_id`). Top-K is bounded (`DEFAULT_TOP_K=10`, `MAX_TOP_K=50`) both at the route (`Query(ge=1, le=50)`, 422 on violation) and defensively inside the use case itself. `list_by_agent_id` (Stage 7) was corrected to filter `status=CURRENT`, honoring the Stage 5 Knowledge Chunk lifecycle that no prior consumer needed to respect yet - not a redesign, a correctness fix in a new consumer.

New route (`app/modules/knowledge/interface/routes.py`), schemas (`SearchResponse`/`SearchResultResponse` - no `embedding_vector` field, by construction, not by omission-review), `AgentNotFoundForUserError` (agent module), and two new exception mappings reachable through a route for the first time (`ProviderConfigurationError`→503, `ProviderRequestError`→502).

20 new tests: 9 unit (agent-not-found, empty-knowledge-base, provenance assembly, no-raw-vector assertion, top-K limiting/clamping/over-request, missing-evidence-link defensive case, and an explicit agent-isolation test), 3 integration (full pipeline-to-search against real SQLite, empty-knowledge-base, and agent isolation with two agents whose chunks embed to identical vectors), 8 e2e (real HTTP: successful search with provenance and no raw vector in the response, 401/422/404 cases, empty-results case, top-K query param, and the explicit cross-agent authorization test the project owner required, run over completely separate authenticated HTTP sessions).
