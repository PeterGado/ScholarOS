# 2026-09-16 — Project Writing Stage 8 Findings Resolved, Backend Committed, Frontend Milestone Started

## Session: Resolving Both Stage 8 Findings (RUNNING Work Item Recovery; Instructions Contract)

**Objective:** Stage 8 (2026-09-15) validated the Project Writing backend end to end but surfaced two findings without resolving them, per its validation-only scope: (1) a `RUNNING` Work Item that crashes mid-processing is never automatically retried - a general, pre-existing ADR-006 characteristic, not Writing-specific; (2) `docs/Project_Writing_Implementation_Plan.md` §19 item 3's 2026-09-12 decision (generation instructions persisted via a Draft-scoped Conversation/Message) was never actually implemented - Stage 7 shipped a plain `instructions` request field instead. Explicitly authorized to resolve both, with direction that the first be treated as a general worker/ADR-006 concern rather than a Writing-specific patch.

### RUNNING Work Item Recovery

Added `WorkItemRepository.requeue_stale_running(stale_after, max_attempts)` (`app/workers/repository.py`) - kind-agnostic (Writing and Knowledge Processing Work Items both benefit), reusing `mark_failed`'s own bounded-retry rule so a Work Item that keeps crashing its worker still terminates in `failed` rather than looping forever. `WorkItemExecutorLoop.start()` (`app/workers/executor.py`) now calls it once, synchronously, before polling begins - deliberately not on every poll tick, so it can never race the item the current process is itself still executing; a stale `RUNNING` row can only be left behind by a *prior* process that crashed or was killed. Default threshold: 10 minutes, configurable via a new `stale_running_threshold` constructor parameter.

### Instructions Contract Resolution

Re-read §19 item 3's original decision text before choosing a resolution path: the 2026-09-12 approval was for Option (b) specifically - persist instructions via the frozen `Conversation`/`Message`/`Message Context Link` entities (04_Logical_Data_Model.md §3.9, §3.10, §4.4), which Stage 2 explicitly deferred building. Rather than re-litigating that decision or retroactively blessing Stage 7's direct-field shortcut, implemented Option (b) as originally specified:

- `Conversation`, `Message`, `MessageContextLink` added as domain entities (`app/modules/writing/domain/entities.py`), ORM models (`infrastructure/models.py`), and repositories (`infrastructure/repositories.py`), following the exact conventions already established for `DraftEvidenceLink`/`MemoryProvenanceLink` (exclusive-arc CHECK constraints, `_enum_column` value-callable pattern).
- `MemoryProvenanceLink.conversation_id` gained the real foreign key it was missing since Stage 2 (deferred at the time because Conversation didn't exist yet) - a small, low-risk consistency fix now that the referenced table is real.
- `RequestDraftGenerationUseCase` (`app/modules/writing/application/generation_request.py`) now finds-or-creates a Conversation per Draft (via the genuinely free-form `title` field, keyed `draft:<id>:instructions` - deliberately not a new `draft_id` column, so the frozen Conversation shape stays untouched) and persists each generation request's instructions as that Conversation's next `Message`, before enqueueing generation.
- The public HTTP contract is unchanged: `RequestDraftGenerationRequest.instructions` is still a plain string field - only the internal persistence mechanism changed, not the client-facing API.
- `EnqueueDraftGenerationUseCase.execute()` and `build_generate_draft_version_payload_reference`/`parse_generate_draft_version_payload_reference` (`app/workers/payloads.py`) gained an optional `message_id`, threaded through the Work Item's `payload_reference` (a new 4th colon-delimited segment; a genuine, intentional breaking format change - no backward-compatibility shim was added for the dev-only SQLite database, consistent with this project's stated preference against such shims).
- The executor's writing branch (`app/workers/executor.py`) now links the instructions Message - and a newly-created system-response Message recording which Draft Version resulted - to that Draft Version via `MessageContextLink`, closing the provenance loop from "what was asked for" to "what was produced."

### Verification

Full regression: 524/524 tests pass (512 prior + 12 new), zero regressions.
